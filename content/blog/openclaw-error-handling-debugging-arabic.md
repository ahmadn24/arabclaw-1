## المقدمة

أكثر ما يُهدر وقتك كمطور ليس كتابة الكود الأول، بل البحث عن سبب توقف الكود عن العمل في منتصف الليل. معالجة الأخطاء في أوبن كلاو (OpenClaw) ليست موضوع ثانوي يمكنك تأجيله — إنها أساس الثقة في أي تطبيق متصل بالعملاء أو البيانات الحساسة.

الفرق بين مطور يقضي ساعات في تتبع خطأ غامض ومطور يحدده في دقائق هو الاستراتيجية. هذا الدليل لن يعطيك حلولاً سحرية، بل سيعطيك إطاراً عملياً لفهم أين تذهب الأمور نحو الخطأ وكيفية التعامل معها بذكاء.

## فهم أنواع الأخطاء في أوبن كلاو

ليست كل الأخطاء متساوية. البعض يأتي من الشبكة، والبعض من المنطق، والبعض من الأذونات. أوبن كلاو يواجه ثلاث فئات رئيسية:

**الأخطاء الشبكية** تحدث عندما يفشل الاتصال بين تطبيقك والخوادم. قد تكون مشكلة توقيت (timeout)، أو انقطاع الإنترنت، أو حتى حظر من جدار الحماية. هذه الأخطاء قابلة للمحاولة — إعادة المحاولة غالباً ما تحل المشكلة.

**الأخطاء المنطقية** تعني أن الكود نفسه سليم، لكن ما تمرره له خاطئ. قد تمرر صيغة JSON غير صحيحة، أو مفتاح API مفقود، أو قيمة حقل خارج النطاق المسموح. هذه الأخطاء نادراً ما تُحل بإعادة المحاولة.

**أخطاء الأذونات** تحدث عندما حسابك لا يملك صلاحية لتنفيذ إجراء معين. قد تحاول استدعاء API لم يتم فعل وصولك إليها، أو استخدام ميزة حصرية للخطة الأعلى.

| نوع الخطأ | السبب الشائع | هل تُعاد المحاولة؟ | الحل السريع |
|-----------|-----------|----------|----------|
| شبكي | انقطاع الإنترنت أو timeout | نعم | إعادة محاولة مع backoff أسي |
| منطقي | صيغة JSON غير صحيحة | لا | راجع التوثيق والبيانات المرسلة |
| أذونات | كلمة مرور أو مفتاح API خاطئ | لا | تحقق من بيانات الاعتماد والصلاحيات |
| حد معدل | تجاوز عدد الطلبات المسموح | نعم | انتظر وأرسل مجموعات أصغر |
| داخلي | خطأ في خوادم openclaw.ai | نعم | انتظر وأعد المحاولة، تحقق من الحالة |

## استراتيجيات المناولة الفعالة

معالجة الأخطاء ليست عن اصطيادها فقط — إنها عن فهم ما الذي يجب أن تفعله عندما تحدث.

### الحاصرات والمحاولات (Try-Catch)

كل استدعاء لأوبن كلاو يجب أن يكون محاطاً بحاصر استثناء. هذا ليس للشعور بالأمان النفسي فقط — إنه لمنع تطبيقك من التوقف التام. عندما يحدث خطأ غير متوقع، يجب أن يسقط تطبيقك بشكل لطيف، وليس بانفجار.

النقطة الحاسمة: لا تحاول اصطياد جميع الاستثناءات بحاصر عام واحد. كن محدداً. إذا كنت تتوقع خطأ معين، اصطده باسمه. هذا يساعدك على:  
1. فهم أي نوع من الأخطاء يحدث فعلاً  
2. الاستجابة له بطريقة مناسبة  
3. تسجيل المعلومات الصحيحة للتصحيح لاحقاً

### إعادة المحاولة مع Backoff الأسي

إذا فشلت المحاولة الأولى بسبب خطأ شبكي مؤقت، فلا تحاول مرة أخرى فوراً — ستفشل مرة أخرى. بدلاً من ذلك، انتظر قليلاً، ثم حاول مرة أخرى. إذا فشلت المحاولة الثانية، انتظر أطول قليلاً.

هذا يُسمى "backoff أسي" — كل محاولة فاشلة تزيد وقت الانتظار بضعف. المزايا:  
- تعطي الخوادم وقتاً للتعافي من المشاكل المؤقتة  
- تقلل الضغط على النظام  
- تزيد فرص نجاح المحاولات الموالية

لكن لا تعد المحاولة إلى ما لا نهاية. حدد حد أقصى — 3 إلى 5 محاولات غالباً ما يكون كافياً. بعدها، توقف واحفظ الخطأ.

### التسجيل المفصل (Logging)

دون تسجيل جيد، معالجة الأخطاء مثل البحث في الظلام. عندما يشتكي العميل من أن شيئاً ما لا يعمل في الإنتاج، ما الذي ستفعله إذا لم تكن تملك سجل الأخطاء؟

سجل المعلومات التالية في كل خطأ:  
- **الوقت الدقيق** (timestamp)  
- **رمز الخطأ** (error code)  
- **رسالة الخطأ** الكاملة  
- **السياق**: ما كنت تحاول فعله عندما حدث الخطأ  
- **معرف المستخدم أو جلسة العمل** إذا كان متاحاً  
- **حالة البيانات**: ما كانت قيم المتغيرات الرئيسية

لا تسجل الأشياء الحساسة (مثل كلمات المرور أو مفاتيح API).

## التطبيق العملي: بناء نظام قوي

لنفترض أنك تبني تطبيق أتمتة بريد إلكتروني (مثل [أتمتة البريد الإلكتروني](/blog/2026-02-16-email-automation-himalaya)) يتكامل مع أوبن كلاو لتحليل الرسائل الواردة. العملاء يعتمدون عليك لعدم فقدان أي بريد.

### الخطوة الأولى: إعداد البيئة

أنشئ ملف إعدادات:

```python
# config.py
import os
from dotenv import load_dotenv

load_dotenv()

OPENCLAW_API_KEY = os.getenv('OPENCLAW_API_KEY')
OPENCLAW_ENDPOINT = os.getenv('OPENCLAW_ENDPOINT', 'https://api.openclaw.ai/v1')
MAX_RETRIES = int(os.getenv('MAX_RETRIES', '3'))
BASE_WAIT_TIME = float(os.getenv('BASE_WAIT_TIME', '1.0'))
LOG_LEVEL = os.getenv('LOG_LEVEL', 'INFO')
```

### الخطوة الثانية: بناء دالة معالجة آمنة

```python
# email_processor.py
import time
import logging
from typing import Optional, Dict, Any
import requests
from config import OPENCLAW_API_KEY, MAX_RETRIES, BASE_WAIT_TIME

logger = logging.getLogger(__name__)

class OpenClawEmailProcessor:
    def __init__(self, api_key: str):
        self.api_key = api_key
        self.headers = {
            'Authorization': f'Bearer {api_key}',
            'Content-Type': 'application/json'
        }
    
    def analyze_email(self, email_content: str, sender: str) -> Optional[Dict[str, Any]]:
        """
        تحليل البريد الإلكتروني باستخدام أوبن كلاو مع معالجة شاملة للأخطاء
        """
        payload = {
            'model': 'claude-3-5-sonnet',
            'messages': [
                {
                    'role': 'user',
                    'content': f'حلل هذا البريد من {sender}: {email_content}'
                }
            ]
        }
        
        for attempt in range(MAX_RETRIES):
            try:
                response = requests.post(
                    'https://api.openclaw.ai/v1/messages',
                    json=payload,
                    headers=self.headers,
                    timeout=10
                )
                
                # تحقق من الحالة
                if response.status_code == 200:
                    logger.info(f'تم تحليل البريد من {sender} بنجاح')
                    return response.json()
                
                # معالجة حالات خطأ محددة
                elif response.status_code == 401:
                    logger.error('مفتاح API غير صالح')
                    raise ValueError('بيانات اعتماد API غير صحيحة')
                
                elif response.status_code == 429:
                    # حد معدل — أعد المحاولة
                    wait_time = BASE_WAIT_TIME * (2 ** attempt)
                    logger.warning(f'تجاوز حد المعدل. انتظر {wait_time} ثانية')
                    time.sleep(wait_time)
                    continue
                
                elif response.status_code >= 500:
                    # خطأ خادم — قد يتعافى
                    wait_time = BASE_WAIT_TIME * (2 ** attempt)
                    logger.warning(f'خطأ خادم {response.status_code}. محاولة {attempt + 1}/{MAX_RETRIES}')
                    if attempt < MAX_RETRIES - 1:
                        time.sleep(wait_time)
                        continue
                    else:
                        raise ConnectionError(f'فشل الخادم بعد {MAX_RETRIES} محاولات')
                
                else:
                    # خطأ منطقي — لا تعيد المحاولة
                    logger.error(f'خطأ منطقي: {response.status_code} - {response.text}')
                    raise ValueError(f'رد غير متوقع من API: {response.text}')
            
            except requests.exceptions.Timeout:
                logger.error(f'انتهاء المهلة الزمنية في المحاولة {attempt + 1}')
                if attempt == MAX_RETRIES - 1:
                    raise
                time.sleep(BASE_WAIT_TIME * (2 ** attempt))
            
            except requests.exceptions.ConnectionError as e:
                logger.error(f'خطأ اتصال: {e}')
                if attempt == MAX_RETRIES - 1:
                    raise
                time.sleep(BASE_WAIT_TIME * (2 ** attempt))
        
        return None
```

### الخطوة الثالثة: التكامل مع نظام المراقبة

```python
# monitoring.py
import logging
from datetime import datetime
import json

class ErrorMonitor:
    def __init__(self, log_file: str = 'errors.log'):
        self.log_file = log_file
        self.setup_logger()
    
    def setup_logger(self):
        self.logger = logging.getLogger('openclaw_errors')
        handler = logging.FileHandler(self.log_file)
        formatter = logging.Formatter(
            '%(asctime)s - %(levelname)s - %(message)s',
            datefmt='%Y-%m-%d %H:%M:%S'
        )
        handler.setFormatter(formatter)
        self.logger.addHandler(handler)
        self.logger.setLevel(logging.DEBUG)
    
    def log_error(self, error_type: str, details: dict):
        """
        تسجيل الخطأ مع السياق الكامل
        """
        entry = {
            'timestamp': datetime.utcnow().isoformat(),
            'type': error_type,
            'details': details
        }
        self.logger.error(json.dumps(entry, ensure_ascii=False, indent=2))
```

## أفضل الممارسات والنصائح

بعد سنوات من العمل مع أنظمة متصلة بالإنترنت، تعلمت عدة دروس:

**1. لا تتوقع الكمال**  
الأخطاء حتمية. بدلاً من محاولة منع جميع الأخطاء، بني نظاماً يتعافى منها. هذا أكثر واقعية.

**2. المراقبة أهم من المنع**  
لا تستطيع إصلاح ما لا تستطيع رؤيته. استثمر في السجلات الجيدة والتنبيهات. إذا كان لديك عملاء حقيقيون، يجب أن تعرف عن المشاكل قبل أن يخبرك بها العملاء.

**3. اختبر الأخطاء، لا فقط المسارات السعيدة**  
كل مطور يختبر ما يحدث عندما يعمل كل شيء. عدد قليل يختبرون ما يحدث عندما يفشل كل شيء. اختبر الأخطاء.

**4. وثق قيود API**  
أوبن كلاو، مثل أي API، لديها حدود. وثق حدود معدل الطلبات، الحد الأقصى لحجم البيانات، وقت المهلة. معرفة هذه تجنبك الكثير من المفاجآت.

**5. استخدم نفس الخطأ مع العملاء**  
عندما تقول للعميل "حدث خطأ ما"، لا تعطيه معلومات مفيدة. اعطهم رمز خطأ معين، حتى لو كان بسيطاً. هذا يساعد في التشخيص لاحقاً.

إذا كنت تبني تطبيقاً معقداً يتطلب منطق معقد متكامل مع قنوات متعددة (مثل [أتمتة واتساب مع أوبن كلاو](/blog/2026-02-08-whatsapp-automation-guide))، فإن معالجة الأخطاء تصبح أكثر حرجية. كل قناة قد تفشل بطرق مختلفة، وأنت تحتاج آلية موحدة للتعامل معها.

## الأسئلة الشائعة

### سؤال 1: كم مرة يجب أن أحاول إعادة المحاولة قبل التوقف؟

**الجواب:** الإجابة تعتمد على نوع الخطأ والسياق. للأخطاء الشبكية المؤقتة، 3 إلى 5 محاولات مع backoff أسي عادةً كافية. للأخطاء الحرجة (مثل نقل الأموال)، قد تريد محاولة واحدة فقط ثم التوقف فوراً. القاعدة الذهبية: إذا كانت إعادة المحاولة آمنة ولن تسبب مشاكل (مثل إرسال نفس البريد مرتين)، فأعد المحاولة. إذا كانت خطرة، فقف واطلب من المستخدم.

### سؤال 2: هل يجب أن أسجل جميع الأخطاء أم فقط الأخطاء الحرجة؟

**الجواب:** سجل كل شيء في البداية. التسجيل الزائد أفضل من التسجيل الناقص. عندما تكون في الإنتاج وتواجه مشكلة، ستتمنى أن تملك المزيد من المعلومات، وليس أقل. لاحقاً، عندما تفهم نمط الأخطاء، يمكنك تصفية السجلات وحفظ المساحة. لكن في البداية، تسجيل شامل يوفر عليك الكثير من المتاعب.

### سؤال 3: كيف أميز بين خطأ مؤقت يستحق إعادة محاولة وخطأ دائم؟

**الجواب:** الأخطاء المؤقتة عادة ما تأتي من الشبكة (timeout, connection refused, 5xx) أو حدود المعدل (429). الأخطاء الدائمة عادة ما تأتي من البيانات الخاطئة (400, 401, 403) أو المنطق (validation errors). طريقة سهلة: إذا كانت المحاولة الثانية بنفس البيانات ستفشل بنفس الطريقة، فهو خطأ دائم. إذا كانت قد تنجح، فجرب إعادة المحاولة.

### سؤال 4: هل يمكن إخفاء معلومات الخطأ من المستخدمين النهائيين؟

**الجواب:** نعم، يجب عليك. لا تعرض رسالة الخطأ الفنية الكاملة للعملاء. بدلاً من ذلك، عرض رسالة ودية تقول "حدث خطأ، يرجى المحاولة لاحقاً" وحفظ التفاصيل الفنية في السجلات الخاصة بك. المستخدمون النهائيون لا يريدون معرفة ما هو traceback Python — يريدون معرفة ما إذا كانت المشكلة مؤقتة أم لا.

### سؤال 5: ماذا لو فشل النظام عند محاولة تسجيل الخطأ نفسه؟

**الجواب:** هذا سيناريو نادر لكن حقيقي. الحل: استخدم آلية fallback. حاول التسجيل في ملف، وإذا فشل، حاول إرسال بريد إلكتروني تنبيهي، وإذا فشل ذلك أيضاً، اكتب في وحدة التحكم الأساسية (stdout). الفكرة أنه يجب أن يكون هناك آلية ما، مهما كانت بسيطة، لتتبع ما حدث.

## الخاتمة

معالجة الأخطاء في أوبن كلاو ليست عن الكمال — إنها عن الاستعداد. استعد للفشل، واختبره، وسجله، وتعافى منه بذكاء. الأنظمة الموثوقة لا تُبنى بتجنب الأخطاء، بل بإدارتها بشكل احترافي.

ابدأ بأساسيات: حاصرات محددة، إعادة محاولة ذكية، وتسجيل شامل. ثم بني من هناك. كل مرة تقضيها الآن في فهم كيفية معالجة الأخطاء ستوفر عليك ساعات من الصداع في الإنتاج.

إذا كنت تبني حالات استخدام معقدة مع [تنسيق وكلاء متعددين مع أوبن كلاو](/blog/2026-03-22-multi-agent-orchestration-openclaw)، فإن هذه المبادئ تصبح أكثر أهمية — كل وكيل قد يفشل بطرق مختلفة، وأنت تحتاج فهماً عميقاً لكيفية التعامل مع كل منها.

للمزيد من الموارد والتوثيق الرسمي، زر [openclaw.ai](https://openclaw.ai).

**الخطوة القادمة:** جرب الكود أعلاه في بيئة تطويرك. أنشئ ملف test يحاول تشغيل معالج البريد مع أخطاء مصطنعة (قطع الإنترنت، مفاتيح API خاطئة) وتحقق من كيفية تعامله معها. هذا هو أفضل طريقة لفهم حقيقي.
